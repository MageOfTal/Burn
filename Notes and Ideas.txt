5. Damageable interface / base class
Every destructible object implements take_damage(amount, attacker_id) but there's no formal interface. Objects that should share this:

Tower slabs/chunks
Destructible walls/ramps (also take_damage_at for spatial)
Target dummies
Players (health system)
A Damageable base (or even just a documented interface contract) would let ExplosionHelper and weapon code treat all damageable things uniformly without type-checking.









3. Proximity UI Pattern → ProximityInteractable base or mixin

Three scripts duplicate the same cached-player-lookup + distance-check + Label3D pattern:





world_item.gd — "[E] PICKUP" / "[X] SCRAP"



loot_chest.gd — "[E] OPEN" / "EMPTY"



Tower chunks could use this too

All use _cached_local_player, a 1-second cache interval, and distance-based label visibility. A ProximityInteractable base would provide the cached lookup, distance check, and label management — subclasses just define the prompt text and interaction behavior.

Strong Candidates (Shared patterns, moderate refactoring)

4. Projectile Base Class → ProjectileBase

BubbleProjectile, RubberBallProjectile, and RocketProjectile all share:





launch(direction, speed, shooter_id, damage) entry point



Lifetime timer + queue_free()



Collision handling with damage dealing



Server-authoritative physics



Ammo override system



VFX on destruction (pop/explosion/bounce effects)

Currently Bubble and RubberBall extend PhysicsBodyBase (for mass-weighted push), but Rocket extends raw RigidBody3D. A ProjectileBase that extends PhysicsBodyBase could unify the launch interface, lifetime management, damage dealing, and destruction VFX pattern. Each subclass would override behavior (float, bounce, fly straight).

6. Player Subsystem Base → PlayerSubsystem

All player subsystems (HeatSystem, DemonSystem, KamikazeSystem, GrappleSystem, SlideCrouchSystem) follow the same pattern:





Extend Node with a class_name



setup(player: CharacterBody3D) storing a player reference



Server-side processing + client-side visual processing



Reset/deactivation methods



Synced state via ServerSync

A PlayerSubsystem base would formalize this contract with virtual methods like _server_process(delta), _client_process(delta), and reset(). This also makes it easier to add new subsystems consistently.

Nice-to-Have (Would clean things up)

7. Rarity Damage Bonus (duplicated calculation)

The +15% per rarity tier damage bonus is calculated separately in player.gd (for hitscan combat) and weapon_projectile.gd (for projectile spawning). Should live in one place — either on WeaponData as a method (get_damage_with_rarity() → float) or on WeaponBase.

8. Wall-Check Spawn Offset (duplicated)

The wall-proximity raycast that prevents projectiles from spawning inside walls is duplicated between WeaponProjectile (normal fire) and WeaponHitscan (ammo-override fire path). Could be a shared method on WeaponBase.

9. HUD Widget Extraction

player_hud.gd is 806 lines with multiple _create_*() / _update_*() pairs for compass, kill feed, forfeit ring, heat display, etc. These could each be their own class extending a HUDWidget base, making the HUD more modular and each widget independently testable.

10. Screen Overlay Base

FlashbangOverlay, the scope overlay, and the demon vignette all do the same thing: full-screen ColorRect with MOUSE_FILTER_IGNORE, alpha fade-in/out, intensity/duration parameters. A ScreenOverlayBase would standardize this.
